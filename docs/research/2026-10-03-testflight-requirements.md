# Sortd: what TestFlight needs (checked 3 Oct 2026)

Today is Saturday 3 Oct 2026. Invite date is Friday 9 Oct 2026. Repo read at `main` @ `2659918`. Nothing in the repo was changed.

## Bottom line

The build itself looks ready to upload. The code, entitlements, privacy manifest and export-compliance key all check out (details below). Xcode 27 is a full release (27A266a, 14 Sep 2026, and this Mac runs exactly that), so there is no beta-Xcode problem. The risks are not in the code. They are four things. (1) **Time.** Beta App Review for the first external build is meant to take 24 to 48 hours, but forum posts from June to August 2026 report 4 to 6+ days, and one reports 2+ weeks. If the build is not in review by about Monday 5 Oct, 9 Oct is at risk. (2) **CloudKit.** TestFlight uses the production CloudKit environment, so the `Backup` record type must be deployed there first, or iCloud backup fails for every tester. Nothing in the repo shows that this was done. (3) **Session replay.** Apple's rule 2.5.14 asks for explicit consent and a clear visible sign when a screen is recorded. Sortd turns replay on by default outside the EU/UK/CH, with no first-run question and no on-screen sign. This is the biggest review risk I found. (4) **Paperwork only Raj can do** in App Store Connect: app record, test information, review contact, export-compliance answer if asked. Tips do not need to exist for the beta to pass: the "Leave a Tip" row hides itself until the App Store returns the products.

### Q1. Before ANY upload

- **App record.** Needs platform, name, primary language, bundle ID, SKU, user access. Bundle ID and SKU cannot change later. Only Account Holder, Admin or App Manager can create it. The Account Holder must have signed the latest agreement first. Source: [Add a new app](https://developer.apple.com/help/app-store-connect/create-an-app-record/add-a-new-app). Sure: high. Status: needs Raj (I could not see App Store Connect). Check the name "Sortd" is free there.
- **Agreements.** A free app needs no extra agreement. The Paid Apps agreement is for paid apps and for in-app purchases, even in free apps, and only the Account Holder can sign it. Source: [Agreements help](https://developer.apple.com/help/app-store-connect/manage-agreements/sign-and-update-agreements). Sure: high. For tips to show in TestFlight you also need that agreement Active, banking and tax Active, and a product with name, ID, localisation and price ([TN3186](https://developer.apple.com/documentation/technotes/tn3186-troubleshooting-in-app-purchases-availability-in-the-sandbox)). Sure: high. How long banking and tax approval takes: not verified.
- **Export compliance.** Apple: use of OS-built-in encryption such as HTTPS is exempt from the document upload. Key set to NO skips the question on each build. Apple also says exempt apps "might" owe a year-end self-classification report to the US government ([Apple doc](https://developer.apple.com/documentation/security/complying-with-encryption-export-regulations)). Sure: high on the rule, medium on Sortd's case.
  - Sortd's encryption: HTTPS (Apple networking), CloudKit, Keychain, and CryptoKit. CryptoKit is used for AES-GCM backup encryption (`CloudBackup.swift:526-538`) and SHA-256 hashes (`Analytics.swift:399`, `GoogleAuth.swift:109`). All of that is Apple's own OS crypto, not a custom algorithm, so NO is the usual and defensible answer. It is a legal self-declaration and I cannot decide it for you. Whether the year-end report applies: not verified. Ask someone qualified if unsure. Apple's own table: "encryption limited to Apple OS" needs no documentation ([Apple reference](https://developer.apple.com/help/app-store-connect/reference/app-information/export-compliance-documentation-for-encryption)).
  - One forum thread (Oct 2025, community answers only) says App Store Connect still asked questions with the key set to NO. If asked, answer the questions honestly. Not confirmed by Apple.
  - Status: done (`project.pbxproj:378,416`). Also noted at `docs/AppStoreChecklist.md:181`.
- **Minimum Xcode/SDK.** Since 28 Apr 2026 uploads need Xcode 26 or later with the iOS 26 SDK. Since 9 Sep 2026 iOS apps must target iOS 13 or later (they say "uploaded to App Store Connect", so TestFlight uploads too). Source: [Upcoming requirements](https://developer.apple.com/news/upcoming-requirements/). Sure: high. Sortd: Xcode 27.0 (27A266a) here, deployment target 26.0. Meets it.
- **Beta Xcode.** Not an issue: Xcode 27 is the release build (14 Sep 2026, [App Store Connect release notes](https://developer.apple.com/app-store-connect/release-notes)). Those notes also list TestFlight accepting each Xcode 27 beta from 9 Jun to 28 Sep 2026. Apple's own rule, from a DTS engineer in a forum thread, is that beta-Xcode builds cannot go to the App Store but TestFlight should work ([thread 843433](https://developer.apple.com/forums/thread/843433)). Sure: high for this Mac; medium for the general rule.
- **Missing icon / missing purpose string.** These come back as email errors after upload. I could not load an Apple page for the error codes, so I did not quote any. Sortd has the camera and Face ID strings (`project.pbxproj:376-377`) and an icon file. Run Product > Archive > Validate App before uploading. Not verified in a real archive.

### Q5. Session replay and analytics consent

- **Apple's text.** 2.5.14: "Apps must request explicit user consent and provide a clear visual and/or audible indication when recording." It names "screen recordings". 5.1.1(ii): apps that collect usage data "must secure user consent... even if such data is considered to be anonymous", with an easy way to withdraw. Source: [App Review Guidelines](https://developer.apple.com/app-store/review/guidelines/), updated 8 Jun 2026. Sure: high on the text. Whether Beta App Review enforces it on TestFlight builds: not verified, but 2.2 says betas must follow the guidelines.
- **Sortd today.**
  - Replay is compiled into Release by `SORTD_REPLAY` (`project.pbxproj:430`) and set up at `Analytics.swift:547-556` with text, image and sandboxed-view masking.
  - Consent defaults to ON everywhere except the EU/EEA, UK, CH (`Analytics.swift:372-395`). In Australia, Singapore, Malaysia and the US, recording starts with no question.
  - There is no first-run consent screen. The only control is the Settings > Privacy toggle (`DataControlsView.swift:18-30`). Its caption is "Usage counts, never amounts." It does not say "screen recording".
  - I found no on-screen sign that recording is running (searched `Spend/Views` for replay/recording words; only the developer menu mentions it, `DeveloperMenuView.swift:42`).
  - Disclosure that does exist: `site/privacy.html:171-177` (recordings, 30-day delete, switch) and one closing line in What to Test (`docs/TestFlightWhatToTest.md:51-52`).
- **Gap and options for Raj.** The disclosure is good, but "explicit consent" and "clear indication" are not met by a default-on switch. Either (a) keep replay out of the first external build (remove `SORTD_REPLAY` from the Release settings for now), or (b) add an explicit first-launch choice ("Let Sortd record this beta session? Yes / No") that is off until tapped, in every region, plus a small visible recording dot. (a) is the fast path for 9 Oct. This also touches normal analytics: 5.1.1(ii) asks for consent for usage data too, not only for replay. Default-on outside the EU is a risk for the App Store later. How strict Apple will be: not verified.
- **EU/UK.** Sortd starts off in EU/EEA, UK and CH, which matches the opt-in approach those laws expect. This is general legal knowledge, not an Apple rule and not legal advice. Raj's beta list countries are Australia, Singapore, Malaysia, Other (`docs/BetaEmails.md`), so EU testers are unlikely but possible via "Other".

### Q6. Entitlements and first launch on testers' phones

- **CloudKit.** TestFlight builds use the **production** CloudKit environment. Apple: apps in the App Store "can access only the production environment" and you "must deploy the development schema to the production environment" ([doc](https://developer.apple.com/documentation/cloudkit/deploying-an-icloud-container-s-schema)). A DTS engineer confirms TestFlight uses production, where creating new record types is not allowed, and that the schema must exist in development first ([thread 819507](https://developer.apple.com/forums/thread/819507), Mar-Apr 2026). Sure: high.
  - Sortd's container: `iCloud.com.kameshraj.spend` (`Spend.entitlements:12-15`). Record type: `Backup`, record name `main`, fields `blob` (CKAsset) and `modified` (Date) (`CloudKitBackupStore.swift:10-13`). It fetches by record ID, never by query, so no "queryable" index is needed (the `recordName` queryable error in [thread 814617](https://developer.apple.com/forums/thread/814617) is about queries).
  - The `Backup` type is only created in Development when a development-signed build saves one while signed into iCloud. Nothing in the repo shows this was ever run on a device, and `HANDOVER.md:51` says so. If Development has no `Backup` type, there is nothing to deploy.
  - Do not add `com.apple.developer.icloud-container-environment`. Distribution signing sets production on its own.
  - **Exact steps to deploy:** (1) Run a Debug build from Xcode on a real iPhone signed into iCloud. Settings > Backup & Data > Back up to iCloud, once. (2) Open https://icloud.developer.apple.com/ > CloudKit Database > pick container `iCloud.com.kameshraj.spend` (check the name, a wrong container is the usual mistake) > environment Development > Schema > Record Types. Confirm `Backup` with `blob` and `modified`. (3) Left side: **Deploy Schema Changes**. Review the list. Click **Deploy**. (4) Switch to Production and confirm `Backup` is there. (5) Later, test from a TestFlight build: backup and restore. A team admin does this. As an individual, Raj is the admin ([Apple doc](https://developer.apple.com/documentation/cloudkit/deploying-an-icloud-container-s-schema)). Deploying copies the schema, not records. Production changes are additive: you cannot delete types or fields once deployed, so finish the schema first.
- **App Attest.** Entitlement is `development` (`Spend.entitlements:10`). Apple: "After distributing your app through TestFlight, the App Store... your app ignores the entitlement" and uses production ([doc](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.developer.devicecheck.appattest-environment)). Sure: high. So no change is needed. The Worker only accepts the "appattestdevelop" ID when `ENV=dev` (`worker/src/attest.ts:16,72,95`), so a production Worker accepts TestFlight builds. The Worker is not deployed and `ACCOUNT_WORKER_URL` is empty, so TestFlight testers will not hit it yet.
- **App groups.** Present for the app and the widget (`Spend.entitlements:20-23`, `SortdWidget.entitlements:5-8`, same group). The widget's App ID (`com.kameshraj.spend.widget`, `project.pbxproj:496`) must also have App Groups in the portal. Xcode's automatic signing normally does this. Not verified.
- **Sign in with Apple.** In `Spend.entitlements:5-8`. HANDOVER says the App ID has it. Not verified in the portal.
- **Push.** Not used: there is no `aps-environment` key and no push server (`docs/AppStoreChecklist.md:78-80`).
- **Extra first-launch checks for testers.** Keys: PostHog/Sentry keys come from `Secrets.xcconfig` on this Mac (key, host and DSN are all non-empty; I checked only that they are set). Archive on this Mac, not in a fresh worktree or CI, or the build ships with analytics and crash reports off. PostHog host is the US cloud (`us.i.posthog.com`), the privacy page says US, consistent. A Debug-only entitlements file `Spend-Development.entitlements` exists but is unused.

### Q8. Other things first-time developers get stuck on

- **Build stuck "Processing".** Usually minutes. Forum reports in Feb 2026 had builds processing for days ([thread 816210](https://developer.apple.com/forums/thread/816210)). One poster fixed it by uploading a higher build number; the new build finished in 10 minutes while the old one finished 5 days later (search summary, not read in full). Plan one spare build number.
- **"Missing Compliance".** Build waits for an export answer. Answer it in App Store Connect; the Info.plist key avoids it ([statuses](https://developer.apple.com/help/app-store-connect/reference/app-uploads/app-build-statuses)). Sure: high.
- **Installs fail with "requested app is not available".** Reported in May 2026 for a new app record, with no Apple fix posted ([thread 827382](https://developer.apple.com/forums/thread/827382)). Rare. Not verified how it resolved.
- **"Not Available for Testing"** when the provisioning profile lacks the application identifier. Upload a new build ([statuses page](https://developer.apple.com/help/app-store-connect/reference/app-uploads/app-build-statuses)). Sure: high.
- **Invalid Binary** after upload: read the email from Apple, fix, re-upload with a higher build number.
- **Expiry.** 90 days. Plan a fresh build before early Jan 2027.
- **Testers need iOS 26+** because the deployment target is 26.0 (`project.pbxproj:326`). Use a public link filter for iOS 26 and later (as `docs/BetaEmails.md` already says), or testers on older iOS get an install error. Testers also need the TestFlight app.
- **"Missing Beta Information".** Not found as a specific Apple status. The fix for any missing Test Information is to fill the fields in section 3. Not verified as a named status.
- **Same Apple ID problem.** If Raj signs out of Media & Purchases to use a sandbox account, he can lose access to purchased content. Apple suggests a spare test device ([sandbox doc](https://developer.apple.com/documentation/storekit/testing-in-app-purchases-with-sandbox)).
- **One-off:** the age-rating form now has social-media questions (App Store Connect notes, 9 Jul 2026), and Australia's rating moved to 16+ (18 Jun 2026). This is for the App Store listing, not the TestFlight upload. Not verified whether TestFlight asks.
