## Details

Steps, expected and actual for every finding.

### M1. FX day keys use the phone's calendar, so on a Thai (Buddhist) or Japanese calendar no foreign purchase is ever converted

- Where: `Spend/Services/FXService.swift:13` · area money-parsing · severity high · proved
- Input / steps: Phone calendar set to Buddhist (the default for Thailand region) or Japanese. Log any foreign purchase, e.g. a USD 20.00 tap. Harness: FXService.dayString copied verbatim and run with -AppleLocale th_TH@calendar=buddhist and ja_JP@calendar=japanese, date 1_790_000_000.
- Expected: dayString returns "2026-09-22". The Frankfurter URL and the FXRate keys use the Gregorian year, so the purchase gets an audAmount.
- Actual: Buddhist calendar gives "2569-09-22" and Japanese gives "0008-09-22" (harness output). fetchRates builds "/v1/2569-09-17.." (line 255-256), and exactRate/rate (lines 235, 240) look up keys like "USD-2569-09-22" while the server's keys are Gregorian (line 262-264). The keys never match, audAmount stays nil, and audValue counts the purchase as 0 in every total, for good.

### M2. CA$, MX$, R$, NT$ and ₪ (how en_SG, en_US and en_GB phones write those currencies) are not read, so the tap is saved in the local currency

- Where: `Spend/Services/Parsing.swift:12` · area money-parsing · severity high · proved
- Input / steps: Wallet tap text "OXXO MX$500.00 DBS Visa Debit" (also "Tim Hortons CA$12.50 …", "Padaria R$45.00 …", "Aroma ₪45.00 …"). These are the system formatter's output for MXN, CAD, BRL and ILS on en_SG, en_US and en_GB (checked on this Mac). Or LogPurchaseIntent.handle(amount: "MX$500.00").
- Expected: Currency MXN, CAD, BRL or ILS (all four are in Money.supported), then converted.
- Actual: AmountParser.parse("MX$500.00") gives amount 500, currency nil. "A$" inside "CA$" is rejected because of the letter before it. No marker exists for MX$, R$, NT$ or ₪, and the ISO fallback needs 3 letters. For ₪, WalletTapText.money also drops the sign and returns "45.00". The tap then falls back to LocalCurrency.current() (LogPurchaseIntent.swift:175), which for an en_SG phone in Mexico is SGD. MX$500 (about S$35) is booked as S$500.

### D1. An Apple Pay tap the next day merges into yesterday's hand-typed purchase at the same shop and moves it to today

- Where: `Spend/Services/Deduper.swift:55` · area data-backup · severity high · proved
- Input / steps: Day 1 08:00: add 'Starbucks' A$6.50 by hand (cash, card Other). Day 2 08:00: Apple Pay tap 'Starbucks' A$6.50 through TransactionLogger.log.
- Expected: Two purchases, one on each day. A real-time tap 24 hours after a hand-typed row is a new purchase. The 2-day window exists because bank and statement rows carry only a date. A tap and a manual entry both carry the exact time.
- Actual: One row. Deduper.match uses the 10-minute rule only when the source was seen before (lines 47-55), so manual vs tap gets the full 2-day window and name score 1.0. merge() (SpendStore.swift:168-171) then raises the source to tap (trust 2 > 1) and sets t.date = tap date. Day 1 loses the coffee and Day 2 shows just one. Across a month end, the month total changes too. The Shortcut says 'already logged'. The reverse order (tap first, then the hand-typed one the next day, e.g. a scanned receipt) also merges, and the sheet closes as if it saved. Note: whether a manual entry should ever merge more than minutes away is a design call. The existing test (SpendTests.swift:157) only covers 6 minutes.

### S1. Statement dates are wrong on Buddhist or Japanese calendar phones (2026 becomes 1483 or 4044), and year-less rows vanish

- Where: `Spend/Services/StatementImport.swift:485` · area statement-import · severity high · proved
- Input / steps: Phone set to the Thai region (Buddhist calendar is the default there) or ja_JP@calendar=japanese. Import 'Date,Description,Amount\n01/09/2026,WOOLWORTHS 3342,-58.30', or the text line '28 Sep  SEVEN SEEDS COFFEE  5.50'.
- Expected: 1 Sep 2026 (Gregorian). '28 Sep' becomes 28 Sep 2026.
- Actual: make() builds the date in Calendar.current, so year 2026 is read as Buddhist year 2026 = 1483 CE (Japanese calendar gives 4044). The purchases are saved centuries away and never show in any month's total. Year-less lines take the year from Calendar.current (2569, or Reiwa 8), fail the 1900...2200 check, and are dropped without counting as skipped.

Total is A$20 too low. With a full refund and two same-amount purchases at one shop, the second run marks the other purchase refunded too.

### D2. A failed manual save leaves the row in the context, so 'Please try again' then Add saves the purchase twice

- Where: `Spend/Services/SpendStore.swift:151` · area data-backup · severity medium · to check
- Input / steps: Storage full. New Purchase 'Coffee' 5, tap Add. context.save() throws and the alert says 'Couldn't Save Purchase. Please try again.' Free space (or just retry), tap Add again.
- Expected: One Coffee 5 purchase. A failed save is rolled back, or the retry reuses the first insert.
- Actual: TransactionLogger.log inserts the Transaction (line 150) before `if save { try context.save() }` (line 151) and never removes it when the save throws. AddTransactionView.save's catch (AddTransactionView.swift:543-547) only sets saveError and keeps `saved == 0`, so Add works again. Hand-typed purchases never de-dupe (Deduper.swift:31), so a second row is inserted. The next save that works writes both rows: double money. Taps are safe here because their replay merges with the pending insert. Statement rows are safe because same-source rows merge.

### D3. An iPhone with an older backup writes over a newer iCloud copy made by another iPhone

- Where: `Spend/Services/CloudBackup.swift:323` · area data-backup · severity medium · to check
- Input / steps: Old iPhone backs up (lastBackup t0). New iPhone on the same iCloud restores (Merge), adds 'Coles' A$20 and backs up (iCloud now holds 2 purchases, modified t0+1 day). The old iPhone opens Sortd again; any save or Back Up Now runs a backup.
- Expected: The old iPhone sees that the iCloud copy is newer than its own last backup and refuses (like restoreFirst) or merges first. iCloud keeps both purchases.
- Actual: usableKey only checks iCloud when `lastBackup == nil \|\| existing == nil`. The old phone has both, so it uploads its 1-purchase copy over the 2-purchase one. A restore at that point brings back 1 purchase. Anything logged only on the new phone is gone from iCloud until its next backup, and anything logged only on the old phone is lost when the new phone overwrites it again. Related to the account reviewer's lastBackup-after-Delete-All test (BugHuntAccountTests.swift:138), but this case needs no Delete All. Single-record design, so how far to guard is Raj's call.

### D4. A store that can't open crashes the app on every launch, with no way to restore or export (lead S-02)

### S4. Screenshot import finds nothing in an Apple Wallet card list or a bank app list grouped under date headers

### U1. A Wallet notification whose shop name has an all-caps word that is also a currency code, followed by a number, is booked in that currency
